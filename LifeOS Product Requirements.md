## **1. Executive Summary**

### **1.1. Назначение продукта**

LifeOS — персональная информационная система, предназначенная для централизованного управления повседневной жизнью пользователя.

Система объединяет планирование, выполнение, регистрацию фактических результатов и аналитическую оценку деятельности.

В отличие от обычных приложений для управления задачами, LifeOS должен обеспечивать взаимосвязь между:

- временем;
- задачами;
- привычками;
- целями;
- личными событиями;
- обучением и развитием;
- физическим и эмоциональным состоянием;
- результатами и историей деятельности.

### **1.2. Основная проблема**

Пользователь вынужден использовать разные инструменты для планирования расписания, записи задач, отслеживания привычек, ведения заметок и анализа результатов.

В результате информация оказывается разрозненной.

LifeOS должен решить эту проблему посредством единой модели данных и взаимосвязанных функциональных модулей.

### **1.3. Продуктовая цель**

Создать систему, которая позволяет пользователю:

1. Планировать день, неделю и месяц.
2. Видеть доступное и занятое время.
3. Управлять задачами и долгосрочными целями.
4. Отслеживать регулярные привычки.
5. Записывать события и личные наблюдения.
6. Учитывать фактически потраченное время.
7. Контролировать нагрузку и отдых.
8. Получать объективную статистику.
9. Получать интеллектуальные рекомендации AI.
10. Корректировать планы на основе исторических данных.

### **1.4. Целевая аудитория**

**Primary User — Individual User**

Один человек, использующий LifeOS для личного планирования и саморазвития.

**Основные характеристики использования:**

- Различные виды ежедневной деятельности.
- Необходимость совмещать обучение, работу и личные дела.
- Потребность в гибком расписании.
- Желание измерять собственный прогресс.
- Необходимость долгосрочного хранения личных данных.

**Важное архитектурное решение:** хотя первая версия предназначена одному пользователю, систему следует проектировать с поддержкой нескольких независимых аккаунтов. Это позволит избежать дорогостоящего перепроектирования при возможном расширении.

### **Модель события**

Событие должно содержать:

- название;
- описание;
- дату;
- время начала;
- время окончания;
- категорию;
- цвет;
- тип времени;
- место проведения (опционально);
- связь с задачей (опционально);
- правило повторения (опционально);
- напоминание;
- статус.

### **Типы событий**

- FIXED — обязательное событие.
- FOCUS — сфокусированная работа.
- PERSONAL — личное дело.
- REST — отдых.
- BUFFER — резерв времени.
- FREE — свободный временной блок.

### **Критически важное правило**

Необходимо различать календарное событие и задачу.

Например:

- «Сдать лабораторную» — задача.
- «Работа над лабораторной с 15:00 до 17:00» — временной блок.
- «Занятие в университете с 09:00 до 13:00» — фиксированное событие.

Одна задача может иметь несколько временных блоков.

Этот раздел определяет поведение системы при любых обстоятельствах. Он особенно важен для предотвращения логических ошибок и противоречий между модулями.

## **4.1. Пользователь и данные**

| ID     | Правило                                                  |

**User**

Корневая сущность владения данными

user_id → User

user_id → User

user_id → User

user_id → User

## **6.3. Общие поля моделей**

Для большинства сущностей:

| Поле        | Тип      | Назначение               |
| ----------- | -------- | ------------------------ |
| id          | UUID     | Уникальный идентификатор |
| user_id     | FK       | Владелец                 |
| created_at  | DateTime | Дата создания            |
| updated_at  | DateTime | Последнее изменение      |
| is_archived | Boolean  | Архивирование            |

Не все модели обязаны иметь одинаковый набор полей. Например, для журналов и исторических записей потребуются дополнительные поля.

### **Почему UUID?**

- Удобнее при синхронизации устройств.
- Не раскрывает последовательность внутренних ID.
- Удобен для API.
- Упрощает импорт и экспорт.

## **6.4. Особое внимание к историческим данным**

Я рекомендую использовать три подхода:

1. Soft Delete — для сущностей, которые могут понадобиться в истории.
2. Immutable Logs — записи фактического выполнения не перезаписываются без сохранения истории корректировок.
3. Audit Trail — фиксация важных изменений.

Например, если пользователь изменил привычку «Читать 20 минут» на «Читать 30 минут», старые HabitLog должны продолжать хранить первоначальное целевое значение, действовавшее на момент выполнения.

Это принципиально важно для корректной аналитики.

# **8. AI Architecture — архитектура искусственного интеллекта**

Поскольку ты выбрал AI уже для первой версии, я предлагаю не подключать AI напрямую к моделям Django.

Нужен отдельный AI Service Layer.

## **8.1. Архитектура**

**React AI Assistant**

Пользовательский запрос

**AI API Endpoint**

Проверка пользователя и контекста

**AI Orchestrator**

Контекст · Инструменты · Ограничения · Prompt Management

**LifeOS Services**

Чтение и предложения операций

**LLM Provider**

Генерация и анализ

**User Confirmation**

Подтверждение предложенного действия

**Business Services + Database**

Проверка правил и сохранение данных

## **8.2. AI Use Cases**

| Сценарий           | Пример                              |
| ------------------ | ----------------------------------- |
| Quick Capture      | Превратить текст в задачу           |
| Schedule Planning  | Предложить расписание               |
| Task Breakdown     | Разбить большую задачу              |
| Daily Summary      | Подготовить итог дня                |
| Weekly Insights    | Найти закономерности                |
| Habit Analysis     | Проанализировать регулярность       |
| Overload Detection | Обнаружить потенциальную перегрузку |

## **8.3. Принцип работы с действиями AI**

Например, пользователь пишет:

«В среду нужно сходить в университет с 10 до 14, вечером закончить лабораторную».

AI должен:

1. Распознать дату.
2. Распознать два предполагаемых действия.
3. Определить, что первое является событием.
4. Определить, что второе является задачей.
5. Уточнить недостающую информацию, если она необходима.
6. Сформировать черновик.
7. Показать пользователю.
8. После подтверждения вызвать соответствующие backend-сервисы.

AI не должен самостоятельно записывать произвольные SQL-команды или обращаться к базе данных в обход бизнес-логики.

## **8.4. AI Provider Abstraction**

Не рекомендую жёстко привязывать систему к одному поставщику моделей.

Нужен интерфейс провайдера:

```
AI Provider Interface
       |
       +-- OpenAI Provider
       |
       +-- Other Cloud Provider
       |
       +-- Local LLM Provider
```

Это позволит использовать облачные модели для сложных задач и локальные модели для отдельных сценариев.

Для приватных записей дневника нужен отдельный механизм согласия пользователя. По умолчанию AI должен получать только тот контекст, который необходим для конкретного запроса.

# **11. Internationalization — мультиязычность**

Ты выбрал RU / EN / KG.

Я предлагаю реализовать полноценную интернационализацию с самого начала.

| Язык     | Код | Назначение           |
| -------- | --- | -------------------- |
| Русский  | ru  | Основной язык        |
| English  | en  | Английский интерфейс |
| Кыргызча | ky  | Кыргызский интерфейс |

Для кыргызского языка в международных программных стандартах используется код `ky`, а не `kg` (который обозначает страну).

### **Требования**

1. Возможность смены языка без перезагрузки всей системы.
2. Сохранение предпочтительного языка пользователя.
3. Перевод всех системных сообщений.
4. Перевод статусов и категорий.
5. Локализация дат и чисел.
6. Поддержка часового пояса пользователя.
7. Поддержка 12- и 24-часового формата.
8. Возможность расширения списка языков.

### **Важное техническое решение**

В базе данных необходимо хранить стабильные системные значения:

```
TASK_STATUS:
    TODO
    IN_PROGRESS
    COMPLETED
    POSTPONED
    CANCELLED
```

А не русские или английские названия статусов.

Перевод выполняется на уровне интерфейса. Это позволит сохранять совместимость данных между разными языковыми версиями.

# **12. Testing Strategy — стратегия тестирования**

Я рекомендую не откладывать тестирование до завершения проекта.

Для LifeOS нужны следующие уровни.

**1. Unit Testing**

Обязательно

Проверка отдельных функций, формул и бизнес-правил.

Пример: расчёт Habit Consistency, проверка временных конфликтов.

**2. Integration Testing**

Обязательно

Проверка взаимодействия моделей, сервисов, базы данных и API.

Пример: создание задачи с подзадачами и связью с целью.

**3. API Testing**

Обязательно

Проверка HTTP-кодов, сериализации, прав доступа и ошибок.

Пример: пользователь A не может получить задачу пользователя B.

**4. Frontend Testing**

Обязательно

Проверка компонентов, форм, состояния интерфейса.

React Testing Library и Vitest.

**5. End-to-End Testing**

Обязательно

Проверка полного пользовательского сценария.

Playwright: авторизация → создание задачи → выполнение → аналитика.

**6. Security Testing**

Обязательно

Проверка доступа, токенов, валидации и утечки данных.

**7. Performance Testing**

Перед релизом

Проверка скорости API, Dashboard и аналитики.

### **Обязательные тестовые сценарии**

Особое внимание уделить следующим случаям:

| Сценарий                               | Ожидаемое поведение                   |
| -------------------------------------- | ------------------------------------- |
| Событие заканчивается раньше начала    | Ошибка валидации                      |
| Два фиксированных события пересекаются | Предупреждение о конфликте            |
| Два активных таймера                   | Второй запуск отклоняется             |
| Повторное выполнение привычки за день  | Проверка правила дублирования         |
| Задача отменена                        | Не считается провалом                 |
| Задача перенесена                      | История переноса сохраняется          |
| Пользователь запрашивает чужой ID      | Доступ запрещён                       |
| Нет записей за неделю                  | Пустой отчёт без ошибки               |
| AI вернул неправильную структуру       | Ответ не выполняется                  |
| Потеря соединения при таймере          | Сессия восстанавливается              |
| Изменение часового пояса               | Временные записи остаются корректными |

### **Минимальные критерии качества**

Я предлагаю следующие ориентиры:

- 100% тестов критических бизнес-правил.
- 100% тестов проверки изоляции пользовательских данных.
- 100% тестов основных API-сценариев.
- Не менее 80% покрытия бизнес-логики.
- Отсутствие известных критических и высоких уязвимостей перед релизом.

Покрытие тестами само по себе не доказывает правильность системы, поэтому отдельно нужны проверки граничных случаев.

## **15.1. Решения, которые я рекомендую принять дополнительно**

**A. Как организовать локальную и облачную версии?**

Я предлагаю на первом этапе не делать двустороннюю синхронизацию. Локальная и облачная версии будут самостоятельными окружениями с возможностью экспорта и восстановления данных.

**B. Как обрабатывать дневник через AI?**

По умолчанию AI не получает доступ ко всему дневнику. Пользователь сам выбирает записи или разрешает использование определённых данных.

**C. Как хранить историю?**

Я рекомендую не удалять завершённые события и записи привычек физически при обычном архивировании. Для удаления личных данных должна быть отдельная процедура.

**D. Как рассчитывать продуктивность?**

Не вводить общий рейтинг жизни. Использовать независимые метрики: задачи, привычки, время, цели, отдых.

**E. Как реализовать уведомления?**

В V1 предусмотреть внутренние уведомления и систему напоминаний. Push-уведомления для браузера можно реализовать отдельным этапом.

# **17. Итоговая оценка концепции**

Моя оценка: выбранное направление правильное, но проект достаточно большой.

Я бы особенно выделил три вещи:

1. **Ядро LifeOS — это не AI, а качественная модель данных.** Если события, задачи, привычки и время будут связаны неправильно, никакая AI-модель не исправит аналитику.
2. **Аналитика должна быть объяснимой.** Каждый процент и каждый график должны иметь понятный источник и формулу.
3. **Пользовательский опыт должен быть простым.** За сложной архитектурой не должен скрываться сложный интерфейс.

Для первой версии я бы сосредоточился на сценарии:

`Plan → Execute → Track → Reflect → Improve`

Именно этот цикл должен стать фундаментом LifeOS.
